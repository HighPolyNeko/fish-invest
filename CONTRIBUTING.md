# Работа с ветками и релизами

Схема: `develop` — корень. От него отрезаются `feature/*` и `release/*`. `main` — только указатель на версии, ушедшие на прод, своих коммитов у неё нет.

## 1. Ветки

| Ветка | Откуда | Назначение |
|---|---|---|
| `develop` | — | Корень. Сюда идут все готовые фичи |
| `main` | — | Только догоняет коммит релиза, ушедший на прод |
| `release/1.4.2` или `release/1.4.2-JIRA-789` | `develop` | Релиз-кандидат. Версия первой, тикет (если есть) после дефиса |
| `feature/JIRA-123-short-description` | `develop` | Задача. Живёт 1–3 дня |
| `fix/1.4.2/JIRA-456-short-description` | `release/1.4.2` | Баг, найденный QA |

Имена: строчными, через дефис, описание на английском. Если тикета нет, ключ опускается: `feature/short-description`.

## 2. Способы мержа

- Фича → `develop`: **squash**.
- Фикс → релиз: **squash**.
- Релиз → `develop` (back-merge): **обычный merge-коммит**, не squash.
- Релиз → `main`: **fast-forward only**.

На `develop` линейная история не включается (иначе back-merge невозможен). Договорённость: фичи только squash, merge только для возврата релиза.

## 3. Заголовки PR и коммитов

Conventional Commits: `тип(JIRA-123): описание` (ключ тикета в скобках, если он есть).
Типы: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `ci`, `build`, `perf`, `style`, `revert`.
Заголовок PR = сообщение squash-коммита. Проверяется в CI.

Back-merge: `chore(JIRA-789): вернуть фиксы релиза 1.4.2 в develop`.

## 4. CI

- Проверка (`ci.yml`) на каждый PR и на пуш в `develop`, `release/**`, `main`.
- Проверка заголовка PR (`pr-title.yml`).
- Продвижение `main` (`promote-main.yml`) — ручной запуск после выката релиза, только `--ff-only`.
- Деплой на тест и прод пока не настроен: нужна договорённость, куда выкатывать.

## 5. Процесс релиза

1. Отрезать `release/X.Y.Z` от `develop`.
2. Выкатить на тест.
3. Баги: `fix/X.Y.Z/...` → PR со squash в релиз → перепроверка.
4. Выкат на прод.
5. Запустить `promote-main` с именем релизной ветки: `main` догоняет коммит релиза.
6. Back-merge релиза в `develop` (merge-коммит).
7. Релизную ветку не удалять или поставить тег.

## 6. Настройки GitHub (делает админ репозитория)

Правила (Settings → Rules → Rulesets):

| Ветка | Прямой push | Вход | Особое |
|---|---|---|---|
| `develop` | запрещён | PR, 1 апрув, зелёные проверки | разрешены squash и merge |
| `release/**` | запрещён | PR из `fix/...`, 1 апрув, зелёные проверки | только squash |
| `main` | запрещён | пуш только от `promote-main` (bypass для бота/админа) | без merge-коммитов |

Везде: запрет force push; `develop` и `main` нельзя удалять. Обязательные проверки: `CI` и `PR title`.
В настройках PR включить «Default to PR title for squash merge commits».
Default branch репозитория — `develop`.

## 7. Без прав админа

- Короткие ветки на 1–3 дня.
- Перед мержем обновлять ветку через `git rebase develop`, не merge.
- Номер задачи в заголовке PR.
- История релизов: `git log --first-parent`.
